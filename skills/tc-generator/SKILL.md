# Test Case Generator

Primary use case: a solo developer who wants a testing guide that doesn't skip unhappy paths — not a team artifact by default. Optimized for fast personal review, not for formal documentation someone else has to parse.

## Command

```
/tc [source]
```

`source` is optional — auto-detected if omitted.

## Step 0 — Personal or team?

Ask only if not obvious from context (e.g. no prior signal in this project). Default: **personal**.

- **Personal** → optimize for speed: an actionable checklist the author can tick off themselves, minimal formatting overhead.
- **Team** → see "Team mode" below; structure changes meaningfully.

## Step 1 — Detect source context

Check in this priority order:
1. A spec generated by `/sdd-new` (or equivalent) for the relevant story → use it.
2. Acceptance criteria from a refinement step (Given/When/Then, e.g. an `AI-DATA` block from `us-refinement`) → use it.
3. Neither found → fall back to scanning the code itself.

Tag the output with a confidence level: **high** if it came from an explicit spec or acceptance criteria (real business intent), **low** if inferred from code alone (no guarantee it reflects actual intent — mark these cases as "requires human review").

## Step 2 — Generate two tracks

**Track A — Unit test suggestions.** Only generate this track if the code exists without accompanying tests (no TDD was followed). Reason about it the way a developer would: functions/methods, branches, boundary values. Format to match the project's actual test framework if detectable (e.g. Pest for PHP, Vitest/RTL for React) — otherwise leave framework-agnostic.

**Track B — QA manual checklist.** This is the primary track for personal use. Think from outside the code, not from code structure — what could break this from the UI/API: invalid inputs, field limits, permission edges, mid-flow states, multi-step race conditions. Structure each case as:

- Precondition
- Numbered steps
- Expected result

Group into: happy path / edge cases / negative-error cases. Be explicit — don't rely on the reader inferring an implicit case from a similar one.

## Step 3 — Output

Personal mode: a single markdown file, `test-cases-<id-or-slug>.md`, with two sections (Unit suggestions / QA checklist). No GitHub write-back.

## Team mode

See `references/team-mode.md` — not the default; only apply when Step 0 resolves to team.
